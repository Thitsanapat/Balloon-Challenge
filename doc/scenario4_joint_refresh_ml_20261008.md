## Paired test of the joint-refresh candidate

The experimental `Scenario4ReachableRefreshAgent` keeps the selected guarded
controller. When a committed spline from the observed rocket state fails the
public thrust/tilt/slew feasibility check, it jointly re-solves arrival
velocities and accelerations for the **whole same route at unchanged
deadlines**. Its separate actuator-preview gate was screened rarely and
flagged no flight in these tests. Therefore any observed gain is from joint
derivative refresh, not evidence that the preview predicts true miss distance.

The source/config were frozen for all four fresh paired seeds. Each cell is a
complete official Scenario-4 simulator flight with an unchanged-source check.

| Predeclared seed | Reviewed standalone | Joint-refresh candidate | Difference |
| ---: | ---: | ---: | ---: |
| 1552368575 | 7 | 7 | 0 |
| 1991638024 | 4 | 5 | +1 |
| 1020145031 | 5 | 5 | 0 |

| **Four-flight total** | **18** | **19** | **+1** |

The candidate wins one pair, ties three, loses none; the observed difference
is only +0.25 pop per flight. On the three familiar development seeds the
same candidate scored 6/4/4 versus 5/4/3, but those seeds informed
development and are not independent validation. The four-pair result is too
small to establish a dependable qualification advantage or justify replacing
the reviewed standalone agent. The candidate is still multi-file and would
also need a reproducible standalone/review package before live use.

## Rejected forecast composition

`Scenario4JointAccelerationGuardedAgent` combined the above refresh with the
previous observation-derived acceleration forecast only for a committed
target within three seconds. On development seed 2 it scored **3** versus
**4** for joint refresh alone. The forecast correction was exercised on 1,618
calls, joint rescue on eight, and the source stayed unchanged during the
complete flight. It reached different balloons (#23/#92/#70 versus
#59/#81/#88/#12), despite lower mean observed spline-tracking error
(0.406 versus 0.519 m). This is another concrete case where smoother
tracking/forecast correction did not increase actual pops. Stop this variant;
do not tune it repeatedly against seed 2. Report:
`s4_joint_acceleration_guarded_dev_seed2_20261008.json`.

## Offline machine-learning pilot

`scripts/diagnose_route_capture_ml.py` reads the parity-audited, observation-
only route-shadow v2 archive generated by the frozen PPO parent. It joins the
*first chosen decision* of each executed leg to the subsequent observed
hit/miss outcome. It rejects unaudited or digest-mismatched streams and does
not mark unflown proposals as failures. Six physics/geometry features feed
a strongly regularized logistic model; normalization and fitting exclude the
entire test field in each leave-one-field-out fold. The fitted prototype is
saved in a credential-free diagnostic report, **not connected to a flight
agent**.

| Ten-field, 61-attempt cross-validation | Constant training-fold hit rate | Small learned model |
| --- | ---: | ---: |
| Brier score (lower better) | 0.2615 | 0.2334 |
| Log loss (lower better) | 0.7164 | 0.6600 |

There were 34 active-target hits and 27 misses. The learned Brier score was
better on six of ten left-out fields and worse on four. This is a modest
predictive signal, **not** a measured score gain: the data come from a
different PPO controller, are only 10 independent fields, and contain no
true outcomes for target routes that the controller did not fly. A route
selector trained directly on those missing counterfactuals would have a
serious selection-bias problem. The archive SHA-256 is
`0c0d0a86f64a06ca2007caf2346d8c49837c8a299db8d116385e4a843b3f4619`;
the report is ignored local
`evaluation/results/route_capture_ml_group_holdout_20261008.json`.

## Decision and next development step

Keep the reviewed standalone agent for qualification (SHA-256
`dab27623c797c70c6fc5c13b48e4faa2e146a694c7de737f6cae8138485fb333`).
The strongest short-term improvement candidate is still full-route joint
refresh, but its +1 across four fresh fields is not compelling enough to
promote. A larger PPO network or long GPU run is unlikely to help immediately
if it only perturbs low-level acceleration: the previous frozen residual PPO
improved its own base by 0.9 pop/flight in a 10-field holdout, but continued
training yielded only +1 across three further fields and preview MPC lost a
later 10-field holdout. None of those tests compared PPO directly with the
currently reviewed guarded agent on the same seeds.

For a learned **route** model, next collect many more independent training
fields under the selected controller (or a clearly specified safe exploration
policy), label only executed outcomes, and measure group-held-out calibration
before integration. Keep the physical feasibility validator and the reviewed
controller as fallback. Then compare the frozen learned selector against the
current agent on new paired official fields, reporting low-score failures as
well as mean pops. This is a path to a potentially higher score, not a promise
of 20; simulator reset/data throughput is the immediate bottleneck, not GPU
memory. Any GPU job must obey the previously agreed one-card limit.
